# Threat model

Protected assets are credentials, capital, broker authority, market and portfolio state, immutable evidence, holdouts, risk controls, and qualification decisions. Trust boundaries include providers, environment configuration, local files, SQLite, future broker and TradingView inputs, agents, and CI.

Main threats are secret disclosure, path or artifact tampering, stale or conflicting data, lookahead leakage, overbroad research reads, replayed intents, duplicate orders, timeout-after-acceptance resubmission, wrong endpoint or mode, broker drift, forged or reordered broker events, control weakening, premature holdout reads, holdout reuse, and selective evidence. Current controls are no broker writes, offline default, rejected live selection, names-only `.env.example`, ignored runtime data, canonical hashes, atomic immutable artifacts, reconstructible catalog, validation and quarantine evidence, secret scan, review-separated protected controls, range-limited cataloged experiment reads, registry-derived qualification evidence, one-time holdout-run authorization, exact candidate binding, atomic authorization consumption before data access, protected result storage, one-time holdout read access, a strict reviewed paper risk configuration, and a redirect-blocking fixed-origin GET-only paper-state reader with normalized response validation.

M4 must add an exact paper endpoint allowlist, immutable intent receipts, durable idempotency, independent
risk decisions, atomic pending-capacity reservation and single-submitter claims, protected paper
authorization, a strict order envelope, fresh account/position/order/clock/quote snapshots,
forward-only order state, broker-event dedupe, reconciliation, persistent emergency disable, and an
append-only hash-chain journal. An unknown submit, cancel, or cancel-all result is unsafe until lookup
and reconciliation resolve it. Only schema-validated normalized broker fields may be stored; raw
responses, headers, URLs, exception text, and credentials must not enter logs or journal payloads.

The reviewed future mutation boundary permits only one fixed-origin order POST and one exact-order DELETE, disables proxy routing, blocks redirects, limits time and response size, and treats every transport uncertainty as an unknown outcome without retry. This limits credential redirection, SSRF, response flooding, duplicate mutations, and false claims about a failed call. It does not protect credentials or calls from a hostile administrator, compromised system trust store, malicious local process, or compromised Alpaca endpoint.

The candidate research commit and installed execution commit are separate identities. The paper authorization retains the qualified candidate commit; the activation, process opt-in, and fresh installed-runtime proof retain the execution commit. Dropping either binding would allow unqualified strategy code or unreviewed execution code. Both mismatches fail independently.

Intraday Campaign V1 also keeps its sealed reviewed-foundation commit separate from its execution commit. Before a candidate claim, the source review verifies a main-only GitHub-attested wheel, exact installed project bytes, the fixed lockfile's exact dependency wheels and installed files, a CPython 3.12 `venv --without-pip` runtime started through the fixed `-I -B -S` bootstrap, and all 48 application-package Python modules against the wheel-bound surface manifest. The attestation verifier is resolved once to a canonical absolute regular file named `gh`, checked before and after both exact-path calls, and retained by path and SHA-256 in the build identity. Its file and every install-path ancestor must be owned by another trusted account and non-writable by the execution account. The manifest uses exact bytes, not AST normalization, and classifies foundation-exact modules, exact reviewed deltas, and reviewed new files. Added, missing, or mutated modules fail and require Campaign V2. The runtime checks the complete base Python and site trees, executable chain and bytes, import paths and hook identities, timezone, decimal state, and dependency artifacts. Each assessment validates current hook state and loaded origins against those exact trees without persisting the dynamic loaded-module set. It rejects loader environment, startup files, bytecode, unowned paths, symlinks, special files, and unexpected distributions. The manifest is inert and cannot prove itself, so a human must review the full main-attested source commit, wheel, verifier identity, and assessment fingerprint. The registry records one immutable explicit campaign review and atomically binds a fresh matching assessment to each claimed candidate. The runner verifies the same runtime again before report publication, and qualification compares the report evidence with the registry. This path grants no holdout, paper, broker-write, or live authority.

Residual risks: local filesystem access can replace local databases, artifacts, or installed files after verification; the transaction-bound paper runtime fingerprint proves the identity checked within five seconds before attempt creation, not resistance to hostile local code or later local mutation; Campaign V1 snapshots and verifies before claim and report publication but cannot prove that a privileged process transiently changed same-process memory, or that the OS kernel or loader was compromised; its remote attestation can occur only after merge; paper snapshot and lookup attestations prove the local adapter path and journal binding, not resistance to wholesale database replacement; the fixed-origin production coordinator has no operator CLI and process opt-in can open its outer runtime gate, but each attempt still depends on local evidence and the non-hostile-process assumption; shorter restart-safe supervision validation passed, but the remaining 168-hour duration was waived and remains an explicit evidence gap; the fixture calendar handles weekdays rather than exchange holidays; paper-runtime dependency provenance is not attested; Alpaca paper fills do not model market impact, queue position, or full liquidity. The public repository exposes its source and history by design; secrets and runtime data must remain untracked.
