# Threat model

Protected assets are credentials, capital, broker authority, market and portfolio state, immutable evidence, holdouts, risk controls, and qualification decisions. Trust boundaries include providers, environment configuration, local files, SQLite, future broker and TradingView inputs, agents, and CI.

Main threats are secret disclosure, path or artifact tampering, stale or conflicting data, lookahead leakage, overbroad research reads, replayed intents, duplicate orders, timeout-after-acceptance resubmission, wrong endpoint or mode, broker drift, forged or reordered broker events, control weakening, premature holdout reads, holdout reuse, and selective evidence. Current controls are no broker writes, offline default, rejected live selection, names-only `.env.example`, ignored runtime data, canonical hashes, atomic immutable artifacts, reconstructible catalog, validation and quarantine evidence, secret scan, review-separated protected controls, range-limited cataloged experiment reads, registry-derived qualification evidence, one-time holdout-run authorization, exact candidate binding, atomic authorization consumption before data access, protected result storage, one-time holdout read access, a strict reviewed paper risk configuration, and a redirect-blocking fixed-origin GET-only paper-state reader with normalized response validation.

M4 must add an exact paper endpoint allowlist, immutable intent receipts, durable idempotency, independent
risk decisions, atomic pending-capacity reservation and single-submitter claims, protected paper
authorization, a strict order envelope, fresh account/position/order/clock/quote snapshots,
forward-only order state, broker-event dedupe, reconciliation, persistent emergency disable, and an
append-only hash-chain journal. An unknown submit, cancel, or cancel-all result is unsafe until lookup
and reconciliation resolve it. Only schema-validated normalized broker fields may be stored; raw
responses, headers, URLs, exception text, and credentials must not enter logs or journal payloads.

The reviewed future mutation boundary permits only one fixed-origin order POST and one exact-order DELETE, disables proxy routing, blocks redirects, limits time and response size, and treats every transport uncertainty as an unknown outcome without retry. This limits credential redirection, SSRF, response flooding, duplicate mutations, and false claims about a failed call. It does not protect credentials or calls from a hostile administrator, compromised system trust store, malicious local process, or compromised Alpaca endpoint.

The candidate research commit and installed execution commit are separate identities. The paper authorization retains the qualified candidate commit; the activation, process opt-in, and fresh installed-runtime proof retain the execution commit. Dropping either binding would allow unqualified strategy code or unreviewed execution code. Both mismatches fail independently.

Source-reviewed intraday campaigns keep the sealed foundation commit separate from the execution commit. Campaign V1's immutable 48-module review remains historical evidence, but its lifecycle is read-only after the acquisition defect. Closed Campaign V2 used a new plan identity and a 49-module exact-byte surface that included the corrected provider. Before each V2 candidate claim, the source review verified a main-only GitHub-attested wheel, exact installed project bytes, the fixed lockfile's exact dependency wheels and installed files, a CPython 3.12 `venv --without-pip` runtime started through the fixed `-I -B -S` bootstrap, and every application-package Python module in the reviewed V2 build against the wheel-bound surface manifest. The attestation verifier was resolved once to a canonical absolute regular file named `gh`, checked before and after both exact-path calls, and retained by path and SHA-256 in the build identity. Its file and every install-path ancestor had to be owned by another trusted account and non-writable by the execution account. The runtime checked the complete base Python and site trees, executable chain and bytes, import paths and hook identities, timezone, decimal state, and dependency artifacts. Each assessment validated current hook state and loaded origins against those exact trees without persisting the dynamic loaded-module set. It rejected loader environment, startup files, bytecode, unowned paths, symlinks, special files, and unexpected distributions. The manifest was inert and could not prove itself, so a human reviewed the full main-attested source commit, wheel, verifier identity, and assessment fingerprint. The registry recorded one immutable explicit campaign review and atomically bound a fresh matching assessment to each claimed candidate. The runner verified the same runtime again before report publication, and qualification compared the report evidence with the registry. V2 completed 60/60 candidates, failed 12/12 base research qualification groups, and is closed immutable failed evidence.

The V2 manifest remains fixed to that reviewed source and does not cover V3. V3 uses a separate exact-byte package surface and a preregistration seal that binds the exposure inventory, period selection, final plan, qualification binding, main source commit, first validation bar, and false authority set. The verifier accepts only the exact repository, signer workflow, main ref, source digest, and seal subject digest from a protected `gh` executable. It derives the effective selection cutoff only from a verified Sigstore transparency-log timestamp and requires it to precede Validation A's first bar. Author-recorded selection dates and local or Git commit time cannot establish freshness. Seal creation and verification run all four artifacts through their shared strict parsers, so a newly known overlapping acquisition cannot be hidden by recomputing fingerprints. This proves prospective publication timing, not universal knowledge. The V3 preassessment separately verifies the attested wheel, runtime manifest, whole-package surface, installed project bytes, fixed lock, dependency wheels, isolated runtime, and verifier identity. A human must bind that exact assessment to the stored seal and plan. Disjoint `intraday_v3_*` tables make the seal, plan, 60 reservations, four dataset roles, stored specs, review, source bindings, publication intents, integrity conflicts, lifecycle, and results immutable apart from guarded lifecycle and publication-owner transitions. All four complete manifests must pass before one atomic bind. Claims use the sole stored review, canonical spec, and an unexposed random lease token. Source is checked again before compute and publication. The registry commits the canonical report intent before its final path, accepts only exact create-only bytes, syncs the containing directory before completion, and lets stale recovery atomically replace the publication owner. The retained intent reconciles a missing completed report; a running mismatched path records terminal failure, and substituted completed bytes create immutable conflict evidence that blocks qualification. Registered qualification derives roles from the sealed plan, verifies every completed source-bound report and every failed reason, fingerprints all 60 sources, and never grants authority. Caller-configured V1 research cannot become V3 evidence.

Residual risks: local filesystem access can replace local databases, artifacts, or installed files after verification; the transaction-bound paper runtime fingerprint proves the identity checked within five seconds before attempt creation, not resistance to hostile local code or later local mutation; Campaign V2 snapshots could not prove that a privileged process transiently changed same-process memory, or that the OS kernel or loader was compromised; V3 prospective freshness cannot prove universal absence of private observation, GitHub/Sigstore and the reviewed main workflow form an external trust base, the preassessment does not prove source correctness or human approval, and package manifests exclude repository files outside the package; paper snapshot and lookup attestations prove the local adapter path and journal binding, not resistance to wholesale database replacement; the fixed-origin production coordinator has no operator CLI and process opt-in can open its outer runtime gate, but each attempt still depends on local evidence and the non-hostile-process assumption; shorter restart-safe supervision validation passed, but the remaining 168-hour duration was waived and remains an explicit evidence gap; the fixture calendar handles weekdays rather than exchange holidays; paper-runtime dependency provenance is not attested; Alpaca paper fills do not model market impact, queue position, or full liquidity. The public repository exposes its source and history by design; secrets and runtime data must remain untracked.
